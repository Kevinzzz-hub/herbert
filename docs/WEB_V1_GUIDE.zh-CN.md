# Herbert Web V1 学习笔记

这份笔记解释 Herbert 网页版为什么这样设计。建议你先理解数据怎么流动，再逐个阅读文件；不需要一开始记住所有语法。

## 1. 用户点击“开始总结”后发生什么

```text
PDF 文件
  ↓（浏览器内）
检查格式、大小、页数，并逐页提取文字
  ↓（只发送约束后的文字和页码）
服务器再次验证输入，按长度分块
  ↓
DeepSeek 分别理解各块，再综合全文
  ↓
服务器检查 JSON 结构和引用页码
  ↓
网页展示概括、核心要点、结论、概念和阅读提示
```

这套流程有两个明确边界：

- 浏览器负责接触用户的原始 PDF，原文件不上传到 Herbert 服务器。
- 服务器负责保管 DeepSeek 密钥，浏览器代码永远读不到密钥。

这也是本次修复大文件问题时最重要的设计决定。样本 PDF 约 2.5 MB；在浏览器提取后，包含页码的请求约 19 KB，传输量减少约 99%。

## 3. 为什么要“浏览器验证一次，服务器再验证一次”

浏览器验证是为了尽快给正常用户反馈，例如文件不是 PDF 或超过 12 MB。服务器验证是安全边界，因为任何人都能跳过网页，直接伪造请求。服务器会重新检查：

- 文件名是否合理；
- 页码是否从 1 连续排列；
- 页数是否超过 120；
- 总文字量是否在 100 到 80,000 字符之间。

这叫“不要信任客户端”。它不是怀疑用户，而是网络应用的基本规则。

## 4. 为什么 AI 总结要分两层

长文档不能稳定地一次读完，所以 Herbert 采用“分块总结 → 全文综合”：

1. 每个分块不超过约 4,000 字符，并保留原始页码标记。
2. 多个分块可以并行请求 DeepSeek。
3. 最后一次请求合并重复信息，提炼 3–7 个核心要点。
4. 程序检查 AI 返回的 JSON；不存在的页码会被拒绝，而不是直接展示。

页码校验只能防止引用一个不存在的页码，不能证明一句话一定正确。因此界面仍提醒用户回到原文核对重要内容。

## 5. 当前版本明确不做什么

- 不做扫描件 OCR；没有可复制文字时提示“此 PDF 暂不适用”。
- 不理解图片、图表和复杂公式。
- 不保存用户、PDF 或阅读历史。
- 暂不做相关知识外延和追问；先把总结主流程做可靠。

明确“不做什么”是项目能力的一部分。它可以防止功能不断扩张，导致最关键的流程没有做好。

## 6. 你接下来最适合做的三个练习

1. 在 `progressSteps` 中修改一句加载提示，观察界面变化。
2. 在 `MAX_FILE_BYTES` 中调整限制，并解释为什么浏览器和服务器都要检查输入。
3. 给结果页添加“复制总结”按钮，并为它补一项自动化测试。

第三项很适合作为你第一次亲手完成的小功能：范围小、结果直观，同时会接触事件处理、浏览器剪贴板 API 和测试。
